Changelog
=========

All notable changes to this project will be documented in this file.

The format is based on [Keep a Changelog](https://keepachangelog.com/en/1.1.0/).
This project ships as a rolling release (Docker image tag `latest`) and does not
yet use version tags, so all entries live under `[Unreleased]`. When a tagged
release cadence begins, dated version sections will be promoted from this list.

## [Unreleased]

### Added
- **`upgrade edge` for main-branch builds.** The broadcast repo now publishes an `edge` image tag built on demand from `main` (a single tag, replaced on every build — no per-commit tags, so registry space stays bounded). `./broadcast.sh upgrade edge` already worked mechanically; it now guards itself: interactively you must type `edge` to confirm you understand it's an unreleased build whose migrations may make a downgrade unsafe, and automated (cron-driven) upgrades refuse the tag outright so a production box can never drift onto it. Dev/throwaway servers only.

### Fixed
- **Restore no longer crashes on installs pinned to a rolling tag.** The restore version gate fed `.current_version` straight into a semver comparison; on a box pinned to `latest` (every fresh install) or `edge`, that was a bash arithmetic error (`10#edge`) that killed the restore under `set -e` before it copied anything. Non-numeric versions now skip the gate with a warning instead.

### Added
- **Auto-recovery now reaches existing installs, and is harder to misfire.** `upgrade` installs the recover cron alongside the health one, so an existing install no longer has to run the manual `fix` command to get it — the customer whose outage motivated the feature would otherwise have upgraded and still had nothing restarting their server. `recover` also now takes a lock (overlapping cron ticks could each bank the same failure count and both restart), bounds every Docker call with a timeout (a wedged `dockerd` otherwise hung a tick forever while cron started another every minute), and treats a missing probe binary as a broken probe rather than a broken app — that was the one path where it would have restarted a perfectly healthy server every 15 minutes, forever.
- **File-descriptor usage is now recorded.** `monitor` writes the app container's open-descriptor count and its limit to `system.json` every minute, and `diagnose` reports both for the app and job containers, warning past 70% of the ceiling. The 2026-08-15 outage was descriptor exhaustion and nothing on the box was counting, so we could not tell a burst that exhausted a low limit from a slow leak that had been climbing for days. The webhook burst that triggered it arrives daily, so a per-burst leak now shows as a step change within a day or two instead of being invisible until the next outage.

### Added
- **The server now restarts itself when the app stops answering.** A new `./broadcast.sh recover` runs from cron every minute, probes Puma directly, and restarts the stack after three consecutive failures. This closes the gap that made the 2026-08-15 incident 31 minutes long rather than three: the app had stopped serving while its process was still alive, so the container stayed `Running`, `restart: always` never fired, and every signal Docker exposes said healthy. The only thing on the box that could see the failure was a direct Puma probe, which until now reported it to a dashboard and did nothing about it.

  Deliberate properties: three consecutive failures before acting, so a brief blip never triggers a restart; it stays out entirely when the app container is **absent or not running**, because that is an upgrade, a stop or a deploy rather than an outage (`upgrade` removes the containers and then pulls a new image, a window of minutes); a **boot grace** of ten probes for any freshly started container, since migrations run before Puma listens and a booting app is indistinguishable from a broken one to this probe; at most one restart per 15 minutes, so a server that cannot stay up is restarted rather than flapped; and it is **independent of health monitoring** — recovery is local and phones nobody, so an install that opted out of telemetry still recovers itself. Operators who want to be the only thing that restarts their server can create `/opt/broadcast/.no_auto_recovery`.

  Every recovery is announced through a single notification seam, so admin alerting can be added later without touching the decision logic. Today that seam writes `/opt/broadcast/logs/recovery.log`, and `diagnose` now reports both its contents and whether auto-recovery is enabled at all — a server quietly restarting itself is the first thing support should know, and the operator will not mention it because it happened without them. Existing installs pick up the cron entry from `./broadcast.sh fix`.

- Stopping the stack now closes lingering database sessions first, and reports which ones it closed (address, client application, state). Postgres under SIGTERM does a *smart* shutdown that waits for clients to disconnect; the image asks for a fast shutdown instead, but compose still only allowed 10 seconds before SIGKILL, and a shutdown checkpoint on a multi-GB database can exceed that on its own. A SIGKILLed Postgres does WAL crash recovery on the next boot, its healthcheck stays unhealthy, and `depends_on: service_healthy` leaves the app container waiting — which is what a "hanging" upgrade looks like from the operator's chair. The sweep runs on `upgrade`, `stop` and `restart`, and is best-effort: an unreachable database never aborts the caller. The named sessions are also the support signal, turning "the upgrade hung" into "we closed a remote client that was idle in transaction".
- Postgres now runs with `idle_in_transaction_session_timeout=10min` and a 60s `stop_grace_period`. An abandoned client transaction (a GUI client left open on someone's desk) holds its locks indefinitely, and because a pending `ACCESS EXCLUSIVE` request also blocks every reader queued behind it, one idle session can wedge the whole app — including the migration that runs on app boot during an upgrade.
- Upgrades now run a preflight and refuse to interrupt work a restart cannot resume. Stopping the service kills a job mid-batch rather than requeuing it, so `upgrade` now checks Postgres directly (not via the app, which may be the thing that is wedged) for jobs a worker has already claimed and for broadcasts in queueing/sending, and reports exactly what is blocking. Queued-but-unclaimed work never blocks: it lives in the database and is picked up again after the restart. An automated upgrade (dashboard trigger or cron) **defers and retries** once the queue drains rather than failing, so a busy night does not become cron failure mail, and `diagnose` warns when an upgrade has been deferred repeatedly so a permanently busy server cannot silently stop upgrading. `./broadcast.sh preflight` runs the check on its own; `./broadcast.sh upgrade --force` is the deliberate operator override. The app enforces the same rules before writing the trigger file at all (see `UpgradeSafety` in the broadcast repo).
- `diagnose` now shows its progress: every collector announces itself before it runs (`[ 1/20] container logs (slowest step on busy servers) ...`) and reports its own elapsed seconds when it finishes, with a total at the end. The command can run for minutes on a busy server and previously printed one line and then nothing until the report — a customer mid-outage reads that as a hang and Ctrl-Cs it, destroying the bundle. Whatever is taking the time now names itself.
- `diagnose` now warns when the system clock is unsynchronized or the NTP service is inactive. Clock skew breaks email provider request signatures and surfaces as authentication failures nobody connects back to the clock; the state was previously printed without comment (observed inactive on a real server).
- `diagnose` now reports **who** holds the database connections, not just how many: a per-source breakdown (client address, database, state, count) plus warnings that name the culprit. Sessions from an address outside the Broadcast containers are flagged as an external client consuming the connection ceiling, and sessions from the docker bridge gateway are flagged as having arrived through the published 5432 port rather than from the app or job containers. A separate warning fires once connection use reaches 80% of `max_connections`. A remote client (psql, a BI tool, an SSH tunnel) starving the app presents exactly like an app hang, and the previous bare active/max counts could not tell the two apart — support had to ask the customer to run SQL by hand.
- Customizing the Docker services is now supported via `/opt/broadcast/docker-compose.override.yml`: Compose merges it on top of the stock `docker-compose.yml` automatically (the systemd unit no longer pins the compose file with an explicit `-f`, which silently ignored overrides). Customers express only their delta, so stock compose changes keep flowing to them. Documented in the README, including the `!override` YAML tag needed to replace list entries such as port bindings (Compose v2.24+). The override file is reported by `diagnose` (contents) and `fix` (presence), and is ignored by git so it never blocks updates.
- `diagnose` now captures the evidence that was missing from a real support case: `git status` of `/opt/broadcast` (a hand-edited file there blocks every update), the installed scripts revision, the override file's contents, and the tails of the nightly update and trigger cron logs.
- `./broadcast.sh help` and the README now point to the hosted CLI reference at https://sendbroadcast.net/docs/cli-reference, which documents every command.
- `./broadcast.sh monitor-enable` / `monitor-disable` control health reporting from the server itself. Disable is a verifiable zero-phone-home switch (creates `/opt/broadcast/.no_health_reports`; the reporter exits immediately while it exists — not even the hourly check-in is sent). Enable removes it, clears any backoff, and checks in immediately.
- Health reporting transmission is now opt-in, not just storage: until the dashboard confirms monitoring is enabled, the install sends only an hourly key+domain handshake with no status, probe, or system data. Installs already reporting are migrated seamlessly.
- `./broadcast.sh health` reports server health to the sendbroadcast.net dashboard for servers that opted in to monitoring there (new cron entry, every minute). Probes each layer (app, web server, HTTPS), applies 3-strike hysteresis so restarts and deploy blips never false-alarm, sends status transitions immediately and steady-state heartbeats on a server-steered interval, spreads fleet traffic with per-domain jitter, and backs off exponentially (dropping reports rather than queuing) when the dashboard is unreachable. Payload is status codes and basic system facts only (disk, memory, load, cores, version, OS, reboot-pending) — never logs, configuration, or subscriber data — and non-opted-in servers stay silent apart from an hourly opt-in check.
- `./broadcast.sh fix` repairs installation drift idempotently: recreates missing directories, restores ownership and executable bits (including the watcher/cleanup helper scripts), the sudoers entry and docker group membership, regenerates a lost `.image` file pinned to the installed version, restores the broadcast user's registry login from stored credentials, installs/enables/starts missing systemd units (verifying each action took effect — a start that did not stick is reported FAIL, never claimed as fixed), recreates the logrotate config, re-adds missing cron entries without touching existing ones, and repairs app/.env essentials (encryption keys, SECRET_KEY_BASE, TLS_DOMAIN from `.domain`, DATABASE_PASSWORD restored from db/.env). Unfixable problems exit 1 and say so: missing Docker or compose plugin (points at a full install), a lost db/.env (the database password is unrecoverable — contact support before restarting), or mismatched database passwords (cannot know which is correct).
- README now documents every `./broadcast.sh` command with what it does and when to use it, grouped by service management, install/update, backup/restore, diagnostics, and configuration.
- `./broadcast.sh diagnose` collects a one-shot support bundle: full container logs (captured first, since a restart destroys them), a noise-filtered app log that surfaces Puma crashes, identity and a brew-doctor-style permission check (ownership, docker group, sudoers), system specs (OS, CPU, memory, disk and inodes, time sync), top processes, port listeners with a warning when a non-Docker web server holds 80/443, live SSL certificate status, Broadcast/image versions with container restart counts, a kernel OOM check, and layered health probes (Puma direct, Thruster HTTP, HTTPS origin via `--resolve`) with an interpretation summary that flags the "container Up but app dead" fingerprint. Also collects job-queue depth and failed-job counts (via postgres, so a dead app container cannot hide its own queue), database connection/size/slow-query state with a pending-migrations check, backup freshness with staleness warnings, per-directory disk attribution, an incident timeline (version/domain history, reboots, failed units, unattended upgrades, container OOM flags), cron liveness, error-only views of the job and postgres logs, and outbound network checks (license server reachability, SMTP egress — commonly blocked on cloud hosts). Prints a delimited copy-paste report (summary, probes, container/system state, filtered log tail) for the support email, plus a tarball with the full logs if support needs to dig deeper — collapsing multi-email diagnostic round-trips into one command.
- Backups now write a `.sha256` checksum sidecar next to the tarball, and `./broadcast.sh restore` verifies it before touching the system — a backup corrupted in transit (offsite download, copy between hosts) is refused before services are stopped. Backups without a sidecar restore as before.

### Fixed
- `diagnose` no longer takes minutes and no longer grows `logs/` without limit. The journal capture is now bounded to the last 7 days (`--since`) instead of scanning the whole journal: under the old json-file driver a "full dump" was capped at 10m x 3 per container, but journald has no such cap, so the same code began scanning multi-GB journals when production moved to it (a 2m12s run and 734MB of `logs/` on a real server). Old diagnose bundles and tarballs are also pruned to the newest 3 — nothing had ever removed them, and each stale bundle made the next run slower. Capture is still bounded by time, never by `--tail`, so a days-old crash stays inside the window. Override with `DIAGNOSE_LOG_WINDOW`.
- `diagnose`'s copy-paste report no longer prints an empty "Top processes by CPU" section. `processes.txt` holds the memory block (17 lines) followed by the CPU block, and the report printed it with `head -20`, which stopped one line into the CPU header — so that section was blank in every real bundle while the data sat unread in the tarball.
- `diagnose`'s connection count now excludes postgres background workers (checkpointer, autovacuum, walwriter), which hold no `max_connections` slot. Counting them overstated connection usage, skewed the new ceiling warning, and added meaningless null-database rows to the per-source breakdown.
- Backups created interactively are no longer at risk of TTY corruption: the backup's `docker compose exec … pg_dump` now passes `-T`. Without it, running `backup_database` at a terminal allocated a pty and pulled the binary dump through it — and since the checksum sidecar is computed afterwards, restore's integrity check could not catch the damage. Non-interactive runs (cron, dashboard trigger) were always safe. The backup also now prints a notice that large databases take several minutes, with the file path to watch for progress.
- Upgrades and downgrades now update the management scripts (`git pull`) **before** stopping the service, so a failed update — a hand-edited file in `/opt/broadcast`, GitHub unreachable — aborts with the site still serving. Previously the pull ran after the stop, and its failure left the site down until a manual restart (the 2026-08-04 customer incident: an edited `docker-compose.yml` blocked the pull and every upgrade attempt took the site down). `update` also now detects local modifications before pulling and explains exactly which files are affected and how to move the changes into `docker-compose.override.yml`, instead of surfacing a raw git merge error — the same hand-edit had made the nightly script update fail silently for weeks.
- `diagnose` no longer reports a false "cron may be dead" warning on healthy servers: cron liveness is now judged by the monitor heartbeat (`app/monitor/system.json`, rewritten every minute) instead of cron log mtimes — successful cron runs emit no output, so their logs stay 0-byte with stale mtimes forever (false positive observed in a real customer bundle).
- A failed upgrade or downgrade no longer leaves the site down until a human runs restart (customer-reported 2026-08-04): everything between the initial `systemctl stop` and the final start ran under `set -e` with no recovery, so any failure in that window — an unreachable registry during the image pull, a failed script update — aborted with the service still stopped. A fail-safe now rolls the image pin back to the previously installed version (already in the local cache, so no registry access is needed) and restarts the service on the way out, turning "upgrade failed" into "upgrade failed, previous version still serving". The upgrade still exits nonzero with the original error.
- Container logs no longer die with their containers: `restart`/`stop` go through `docker compose down`, which removes the containers and — under the old json-file logging driver — destroyed their logs, so the standard remediation for an incident erased the evidence needed for its postmortem (this is how a 2-day production outage lost its logs). Production services now log to the systemd journal (`journalctl CONTAINER_NAME=app`), which survives container removal and reboots; `docker logs` and web-UI log streaming keep working via Docker's default dual-logging cache. `diagnose` now captures from the journal first (full history, including containers a restart already removed) and falls back to `docker logs` on installs whose containers haven't been recreated onto the new driver yet. The driver change reaches existing servers via the nightly script update and takes effect the next time containers are recreated (any restart, upgrade, or reboot).
- A server reboot could leave Broadcast permanently down until someone SSHed in (observed in production 2026-08-03): `pull_policy: always` made `docker compose up` contact the image registry before starting containers, so a boot where the network came up after Docker failed instantly — and systemd's default retry pacing (100ms) burned its 5-starts-in-10s limit within seconds, parking the service in `failed` ("Start request repeated too quickly"). Compose now uses `pull_policy: missing` (boot never depends on the registry; upgrades still pull explicitly), and the `broadcast.service` unit orders itself after `network-online.target`, retries every 5s, and never stops retrying (`StartLimitIntervalSec=0`). The unit template is now delivered to existing installs too: `upgrade` and `fix` rewrite the installed unit whenever it drifts from the current template (previously it was written once at install and never touched again).
- `./broadcast.sh validate_license` no longer appends duplicate registry credential lines to `.env` on every run — existing `BROADCAST_REGISTRY_*` lines are replaced, and unrelated lines are preserved.
- Automatic post-upgrade Docker image pruning never actually ran: the cleanup service starts alongside the stack, slept exactly the 60s stability threshold, and then found the containers a few seconds too young — so it skipped silently on every upgrade (observed: four consecutive skips and 12.7GB of dead images on a production install). The script now polls until the containers have been stable for 60s (up to 10 minutes) before pruning. the compose file's `pull_policy: always` made `docker compose run app` re-pull the image, but restore runs as root, which has no registry login. Migrations now run with `--pull never` against the local image (guaranteed present — the app was running before the restore stopped it). Found by the new smoke-test backup/restore cycle; this very likely broke every real-world restore's migration step until now.
- `./broadcast.sh restore` no longer aborts midway (with services stopped) on current installs: it copied the dump via `docker cp` to a container named `broadcast-postgres`, but the compose file names the container `postgres`. The copy now goes through `docker compose cp` against the postgres service, which is immune to container-name drift.
- Restore steps (loading `.image`, starting postgres, copying the dump, post-restore migrations) now fail the restore explicitly with a clear error instead of falling through — a failed step can no longer end in a "RESTORE COMPLETE" banner with nothing restored.

- README now lists Ubuntu Server 26.04 alongside 24.04 as a supported platform (both are exercised by the VM smoke suite).

- Auto-migration of installations from the legacy `broadcast` registry namespace to `send-broadcast`.
- Docker-based integration tests for backup and restore (`tests/integration/test_backup_restore.sh`).
- Version-compatibility checking in the backup/restore flow so a restore aborts when the on-disk schema is incompatible with the installed image.

- Instant log streaming trigger watcher using `inotifywait` for the web UI's on-demand log viewer.

### Changed
- Copyright notice updated to 2024–2026.

### Fixed
- Web UI log streaming now survives container recreation. `docker logs -f` is bound to a container instance and exited silently whenever `app`/`job` were recreated on upgrade, leaving the viewer stuck on "Streaming / 0 lines" with a stale `application.log`. Each follow is now supervised in a re-attach loop, the watcher runs a periodic flock-guarded `check_log_streaming_trigger` reconcile (the function existed but was never called) to self-heal a dead streamer, and the trigger watch now includes `modify`/`close_write` so clicking Start over a lingering trigger re-arms streaming. `start_log_streaming` is idempotent and `stop_log_streaming` kills the whole process group.
- Upgrades now restart `broadcast-logs-watcher` so updated `logs.sh` / watcher scripts actually take effect — a long-running watcher otherwise keeps the old code in memory across a `git pull` until reboot. Guarded with `|| true` so it can never abort an upgrade.
- Replaced the removed `ntp` package with `chrony` in the installer so fresh installs succeed on Ubuntu 26.04.
- License API response is validated before being parsed with `jq`, surfacing a clearer error when the API returns non-JSON or an error body.
- Database migrations now run automatically after a restore so the app boots against the restored schema.
- Installer fails fast with a helpful error when `.domain` is missing instead of producing confusing downstream errors.
- `DOCKER_IMAGE` is exported during install and image pulls so ARM hosts pick up the correct registry path.
- Update script now re-execs itself after pulling new code so the rest of the run uses the updated logic instead of the stale in-memory copy.

### Fixed
- The `app` and `job` containers now run with a file-descriptor limit of 65536 instead of inheriting Docker's default. Every in-flight request holds several descriptors (inbound socket, proxied connection, database socket), so sustained traffic is sustained descriptor pressure. A customer install ran out on 2026-08-15 when a campaign send produced 1,253 Amazon SES webhooks in 21 seconds: Puma logged `Errno::EMFILE: Too many open files - accept(2)` from its listen loop, the app stopped serving, and the site returned nothing but 502s for 31 minutes until an operator restarted it by hand.

  What made it 31 minutes rather than a blip is that **the failure was invisible to every liveness signal on the box**. The process never exited, so the container stayed `Running`, `restart: always` never fired, `docker ps` showed it Up throughout, and systemd recorded one unbroken run of `broadcast.service`. Part of the process had stopped accepting connections while the rest kept running — the same log shows a SolidCable thread terminating with `Errno::EMFILE` — and nothing in Docker's model can see that. Only recreating the container brought the site back.

  `tests/integration/test_descriptor_exhaustion.sh` reproduces this against the real image, and asserts the combination that matters: exhausted, not serving, and still reporting healthy. The matching cause on the application side (a new SNS signature verifier per request, which re-downloaded Amazon's signing certificate over HTTPS on every webhook, adding an outbound connection to each one) is fixed in the broadcast repo.
